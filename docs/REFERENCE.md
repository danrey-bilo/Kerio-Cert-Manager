## Модули EAMS

развиваются в своих репозиториях, а в проект попадают копией в `modules/<имя>` на закреплённой версии
(`module.json`): весь код для сборки — в этом репозитории, ничего докачивать не нужно.

| Каталог | Версия | Что даёт |
|---|---|---|
| `modules/core` | `0.10.0` | Контракты модулей, `AppDbContext`, транзакции, конверт ошибок, проверка зависимостей при старте |
| `modules/crypto` | `0.5.0` | Мастер-ключ с версиями, конверт секретов AES-256-GCM, перекладка ключей |
| `modules/hosting` | `0.6.1` | Номер обращения, конверт ошибок, фильтр прав «закрыто по умолчанию», пределы частоты, готовность |
| `modules/identity` | `0.10.1` | Пользователи, Argon2id, TOTP, приглашения, сброс пароля, переподтверждение (step-up) |
| `modules/tokens` | `0.8.2` | Сессии: токены доступа и обновления с ротацией, список своих сессий |
| `modules/settings` | `0.8.2` | Настройки: каталог объявлений модулей, база → конфигурация → умолчание |
| `modules/mail` | `0.10.0` | Очередь писем, SMTP (MailKit), шаблоны ru/uk/en, рамка письма, пароль SMTP под шифрованием |
| `modules/audit` | `0.9.2` | Журнал действий только на дозапись с цепочкой хешей, чтение и выгрузка через API |

Новая версия модуля — копией из его репозитория (код, `module.json`, правила сборки; комментарии сокращаются),
затем полный прогон тестов и строка в `CHANGELOG.md`:

```bash
dotnet run tools/copy-module/copy-module.cs -- ../module-core
```

Модуль Kerio ссылается на модуль KeyManager только через публичный контракт `ICertificateSource`: другой
источник сертификатов (не KMP) подключается заменой реализации этого контракта.

## Как сервис решает, ставить ли сертификат

Решение — чистая функция [`DeployPlanner`](../KerioCertManager.Modules.Kerio/Sync/DeployPlanner.cs) от строки
сервера, того, что сервер **подаёт по TLS**, и текущего выпуска KMP. Текущий выпуск имени — **замеченный
позже всех**, а не самый долгий (перевыпуск бывает короче прежнего). KMP вдруг ответил пустым списком при известных
сертификатах — это сбой опроса: снимок остаётся. Выключенный или ненастроенный KMP ничего не отдаёт на установку,
даже из старого снимка, и кнопка «Обновить» отвечает `409`.

| Ситуация | Что делает |
|---|---|
| Сертификат KMP не выбран | Только наблюдение: срок, доступность, предупреждения |
| В KMP нет выбранного имени | Ничего не ставит, письмо «нет в KMP» |
| Сервер подаёт текущий выпуск KMP | Ничего не ставит; если выпуск ещё не записан установленным или отпечаток не тот — **признаёт** его, сверив SHA-256 с выгрузкой из KMP |
| Нажато «Обновить» | Ставит, вопреки выключателям и ручной правке. Если текущий выпуск уже подаётся — ставит заново и проверяет все порты: порт администрирования не говорит за порты служб |
| Сервер не ответил по TLS | Не ставит вслепую |
| Сервис ставил выпуск X, KMP по-прежнему X, а сервер подаёт другой | Ручная правка: не спорит, пишет письмо |
| На сервере чужой доверенный сертификат этого имени действует дольше выпуска KMP | Не заменяет «хуже, чем было» — ни при первой привязке, ни позже; не считается ни ошибкой, ни отставанием |
| В KMP новый выпуск | Ставит — если автоустановка включена в настройках и у сервера; иначе письмо «ждёт установки» |
| Сертификат только что выбран для сервера и ещё не ставился | Ставит и при выключенной автоустановке сервера; общая пауза держит |
| Прошлая установка этого выпуска не удалась | Повтор через 5, 15, 30 минут, 1, 3, 6, 12 часов, затем раз в сутки |
| Пробный режим и этот выпуск уже прогнан пробно | Не повторяет каждый проход |

Причина установки в журнале: `renewal` (продление), `expiring` (на сервере скоро истекает), `initial`
(первая привязка), `manual`, `retry`.

### Очередь установки

Решения дают очередь, а не немедленную установку ([`InstallQueue.cs`](../KerioCertManager.Modules.Kerio/Sync/InstallQueue.cs)):

- **одна установка во всём сервисе** — слот `kerio_install_slot` (одна строка, аренда как у сервера). Проверки
  серверов идут параллельно, ставит только держатель слота; остальные ждут его, держа аренду своего сервера;
- **один сертификат за проход на сервер**; остальные — в `install_queue` сервера по порядку. Пока очередь не пуста
  и API сервера доступен, следующий проход — через `ПаузаПослеИзменения` + 5 с (Kerio успевает перезапустить
  HTTPS), без нового опроса KMP; опрос — не реже интервала. Такой проход трогает только серверы с очередью или
  нажатиями, остальные ждут полного прохода;
- **ожидание слота** — не дольше 90 секунд: занято дольше — имя остаётся в очереди до следующего прохода. Аренда
  сервера — 5 минут и продлевается каждую минуту, пока идёт работа;
- **порядок**: нажатые «Обновить» / «Добавить» — по времени нажатия; затем по сроку того, что сейчас на сервере:
  истёкший, недостающий, истекающий раньше; при равенстве — сертификат по умолчанию, затем по имени;
- **нажатие** — строка `kerio_install_requests` (сервер, имя, кто, когда; повторное нажатие не дублирует): правка
  сервера во время прохода её не затирает. Запрос гасится, когда имени больше нет в очереди — поставлен, не нужен
  или поставить нельзя (API недоступен — с причиной в состоянии сертификата);
- **письма**: проход, увидевший в очереди больше одного сертификата, ставит `queue_report_since`; пока он стоит,
  удача письмом не пишется, а когда очередь опустела — одно письмо `kerio_queue_summary` по журналу установок с этого
  времени. Отказы пишутся сразу;
- пауза перед установкой на тот же сервер — от `last_deploy_at`, а не только внутри прохода;
- лимита на число сертификатов у сервера нет; хранилище Kerio читается целиком.

## Установка и откат

[`KerioDeployer`](../KerioCertManager.Modules.Kerio/Sync/KerioDeployer.cs), шаги и особенности Kerio — в
[KERIO-API.md](KERIO-API.md#установка-сертификата-по-шагам). Главное:

- **до первого запроса к Kerio** проверены ключ (подходит к сертификату), серийный номер (ровно
  запрошенный выпуск, даже если ключ пережил продление), имя, срок, цепочка и защита от отката (выпуск
  не старше установленного);
- сам сервис не ставит, если подаваемый сейчас сертификат не найден в хранилище Kerio: откатываться было
  бы некуда. Исключения — «Обновить» и первая установка после подключения;
- остановка сервиса посреди установки после активации тоже идёт через откат. Хост ждёт до двух минут
  (`HostOptions.ShutdownTimeout`), контейнеру задан `stop_grace_period: 2m30s`. Запись, оставшаяся
  «идёт» после аварийного выхода, закрывается следующим проходом;
- сбой записи шага в журнал установку и откат не прерывает;
- после активации новый сертификат должен появиться **на всех проверяемых портах** за
  `kerio.verify_seconds`; порты мастер находит сам — только те, что подают тот же сертификат;
- проверка — рукопожатием **без SNI**: по имени адреса Kerio подал бы сертификат этого имени, а не по умолчанию;
- не появился — прежний делается активным и проверяется так же; исход `rolled_back` (клиенты успели
  увидеть новый) или `failed` (не успели); загруженный в этот раз новый после подтверждённого отката убирается —
  он истекает позже, и по имени Kerio подавал бы его и дальше;
- прежний сертификат остаётся в хранилище Kerio; уборка старых версий (`cleanup_old`) оставляет
  предыдущий и никогда не трогает подаваемый и встроенный. Убираются только **свои** версии — серийные KMP
  этого имени и выпуски, что сервис ставил (`previous_serials` в базе, до 10, новые первыми), даже если KMP
  при продлении заменил запись; купленный или положенный вручную сертификат того же имени не трогается
  (шаг журнала называет его);
- закреплённый отпечаток TLS после удачной установки переезжает на новый сертификат;
- один сервер одновременно обрабатывает один проход — аренда строки на 30 минут (`lease_until`), без
  долгих транзакций, продлевается перед каждой установкой; проход проверяет до 4 серверов параллельно,
  каждый в своей области — зависший Kerio не задерживает остальные;
- правка сервера, пока его держит проход, — `409` «сервер сейчас проверяется или обновляется»: проход сохраняет
  сервер в конце и молча затёр бы правку;
- ⚠ через ~25 с после импорта или удаления Kerio 10.0.6 перезапускает HTTPS и обрывает сессии API: сессия
  входит заново сама (первый вход ждёт до 15 с, повторный посреди установки — до минуты), а следующая установка
  на тот же сервер начинается не раньше чем через 40 с после прошлой.

### Несколько сертификатов на сервере

Kerio Connect с 9.0.2 хранит сертификаты разных имён и подаёт их по имени, которое назвал клиент (SNI);
сертификат по умолчанию (активный) — когда имя не названо или своего сертификата у имени нет (руководство
GFI «Configuring SSL certificates»). На сервере ведётся **список сертификатов KMP**:

- один можно отметить **по умолчанию** (`common_name`) — он ставится как раньше: активация, проверка на
  всех портах, откат; или оставить сертификат по умолчанию нетронутым;
- остальные — **сертификаты имён** (`extra_common_names`): сервис держит в хранилище их текущий выпуск KMP.
  Порядок установки ([`KerioDeployer.Domain.cs`](../KerioCertManager.Modules.Kerio/Sync/KerioDeployer.Domain.cs)):
  какой сертификат по умолчанию (рукопожатие без SNI) → импорт → сертификат по умолчанию не сменился
  (проверка без SNI; сменился бы — `setActive` прежнего) → проверка с именем в SNI. Обычное продление
  подаётся сразу (Kerio подаёт по имени версию, что истекает позже); перевыпуск короче прежнего мешают свои
  прежние версии — они убираются, и проверка повторяется. Чужую мешающую версию (не из KMP и не ставленную
  сервисом) сервис не трогает — отказ с её названием. Порт из списка проверки не отвечает по TLS, а остальные подают
  новый — установка удалась, с замечанием в журнале и письме: сертификат подаётся, откатывать нечего и перезапуск службы
  не поможет. Не ответил ни один порт — отказ, следующий проход проверит снова. Свои версии — серийные KMP этого имени и все выпуски,
  что сервис ставил (`previousSerials` в `extras` в базе), даже если KMP при продлении заменил запись.
  Уборка (`cleanup_old`) оставляет предыдущую свою версию для ручного возврата.
  Проверено на живом 10.0.6 — протокол в [KERIO-API.md](KERIO-API.md#протокол-опытов-тестовый-1006-31102026);
- доверенный чужой сертификат имени, что действует дольше выпуска KMP, автоматически не заменяется (как и
  сертификат по умолчанию при первой привязке): состояние «в порядке» с пояснением; «Обновить» —
  решение человека — ставит;
- сертификата по умолчанию нет в хранилище — сертификат имени не ставится: вернуть было бы нечего;
- каждый проход спрашивает по SNI каждое ведомое имя (`served_by_name`): свежий выпуск лежит, а по имени
  подаётся прежний — критическое письмо «подаёт не новый сертификат» (нужен перезапуск службы Kerio);
- имя, которого нет в последнем опросе KMP, **не сохраняется**: `400` с `details.field = certificates` и
  `details.problems` — по каждому имени причина и подсказка похожего написания. Уже привязанное и
  пропавшее из KMP имя сохранению не мешает — о нём пишет предупреждение «нет в KMP».

## Хранилище Kerio в обзоре

Каждый вход в API (проход, «Проверить», после установки) читает хранилище Kerio только чтением:
`ConnectCertificate.get` и `toSource` каждого серверного сертификата (отпечаток, серийный, срок, имена).
⚠ Без памяти прошлого прохода: Kerio раздаёт идентификаторы заново, а у перевыпуска то же имя и нередко та
же дата — узнать «тот же» без текста нельзя. Происхождение в обзоре:

| `origin` | Что значит |
|---|---|
| `managed` | Сертификат из списка сервера (по умолчанию или имени) или поставленный сервисом |
| `kmp` | Есть в Key Manager Plus (по серийному номеру), но сервер к нему не привязан |
| `foreign` | Не из KMP: положен в Kerio вручную |
| `builtin` | Встроенный самоподписанный Kerio |
| `request` | Запрос на сертификат |

⚠ Это подпись для людей, не основание для доверия: что подаётся, решает рукопожатие, а «свой» — сверка
отпечатка с выгрузкой KMP.

## Состояния сервера

| Статус | Когда |
|---|---|
| `expired` | Сертификат на сервере истёк |
| `error` | Не прошла проверка: TLS, вход, права, недоверенный сертификат; или выбранного имени нет в KMP |
| `deploy_failed` | Последняя установка не удалась, на сервере старый выпуск |
| `update_pending` | В KMP новый выпуск: в очереди на установку или ждёт кнопки |
| `expiring` | Истекает раньше `kerio.warning_days`, нового выпуска нет |
| `unchecked` | Ещё не проверялся |
| `unbound` | Сертификат KMP не выбран |
| `ok` | Всё в порядке |
| `disabled` | Отключён |

## Письма

Что и когда писать, задаёт вкладка «Оповещения»: у каждого события свой выключатель, у сроков и связи —
пороги. Получатели — общие (`kerio.alert_emails`; пусто — все активные пользователи панели) вместе с адресами
сервера: их правят в «Оповещениях», сохранение не ждёт прохода синхронизации и не будит его. Почта не настроена — писем нет, установка от этого не зависит. Виды сняты с
общего предела частоты почты: повторы гасит сам сервис по `kerio.alert_repeat_hours` (`0` — одно письмо на
каждое появление условия).

| Вид | Когда |
|---|---|
| `kerio_deployed` | Сертификат установлен и подтверждён по TLS — одиночная установка |
| `kerio_queue_summary` | Очередь сервера из нескольких сертификатов опустела: сколько установлено, сколько нет, итог по каждому имени (последний исход: повтор после отказа заменяет отказ). Копится с `queue_report_since` сервера; выключатель — тот же `kerio.alert_deployed`, событие в журнале — `queue_summary`. Ничего не встало — сводки нет: об отказах письма уже ушли |
| `kerio_deploy_failed` | Установка не удалась или откачена — с шагом и причиной; на один выпуск не чаще срока повтора; и в очереди — сразу |
| `kerio_warning` | Скоро истекает, истёк, не обновился сам, нет в KMP, ждёт установки, сменили вручную, недоступен, пароль отвергнут, нет прав, сертификат Kerio не прошёл проверку доверия, для имени подаётся прежний сертификат; пробное письмо. Несколько условий за проход — одно письмо с таблицей, событие в журнале — `alerts_digest` |

| Событие | Выключатель | Пороги |
|---|---|---|
| Скоро истекает | `kerio.alert_expiring` | Первое письмо за `kerio.warning_days`; вход в каждый порог `kerio.alert_reminder_days` (`7, 3, 1`) — новое письмо сразу |
| Истёк | `kerio.alert_expired` | — |
| Не обновился сам | `kerio.alert_overdue` | Продление в KMP не встало за `kerio.alert_overdue_hours` (24 ч) — отсчёт с момента, когда оно замечено, но не раньше подключения сервера |
| Установка не удалась или откачена; выпуск установлен, а для имени подаётся прежний (`name_stale`) | `kerio.alert_deploy_failed` | На один выпуск — не чаще срока повтора |
| Сертификат установлен | `kerio.alert_deployed` | — |
| Ждёт ручной установки | `kerio.alert_pending` | — |
| Сервер недоступен | `kerio.alert_unreachable` | С `kerio.alert_unreachable_checks` (2) неудачных проверок подряд |
| Доступ к Kerio: пароль, права, доверие TLS | `kerio.alert_access` | — |
| Сменили вручную | `kerio.alert_drift` | — |
| Нет в Key Manager Plus | `kerio.alert_source_missing` | — |

Условие ушло — следующее его появление пишется сразу; память об уже ушедшем письме очищает только полный проход
(при недоступном сервере или KMP она сохраняется). Сертификат ещё в очереди на установку — письма о сроке пока нет,
но память держится. Каждое ушедшее письмо — строка журнала оповещений
(`kerio_notifications`, 180 дней): событие, сервер, тема, кому, сколько принято в очередь.

## API

Все адреса — под `/api`, JSON в `snake_case`. «Код» — нужен свежий второй фактор (иначе `403

`5xx`: Cloudflare подменяет их тело).

| `GET` | `/kerio/servers/{id}` | Сервер | |
| `POST` | `/kerio/servers/probe` | Что подаёт адрес по TLS, предложенный режим доверия, порты служб с тем же сертификатом | |
| `POST` | `/kerio/servers/test` | Вход в Kerio до сохранения: роль, версия, хранилище, подсказка имени KMP | |

## Языки

Русский — исходный: на нём написаны панель и сервер. Английский и украинский — словари «русский текст → перевод»:

- **панель** — `t('…')` в коде, словари `KerioCertManager.Web/src/locales/{en,uk}.json`; язык выбирается до
  загрузки разделов (`lib/i18n.ts`), смена — перезагрузка страницы. Выбор — в профиле, хранится личной
  настройкой `ui.locale` (`/api/me/preferences`), после входа панель берёт его оттуда. Проверка полноты —
  `npm run check:i18n` (часть `npm run build`);
- **сервер** — `ServerTexts` модуля Kerio, словари `Localization/{en,uk}.json`: шаблоны с вставками `{0}`,
  вставки переводятся тем же словарём, из подходящих шаблонов — самый точный. `ServerTextTranslation`
  переводит строки JSON-ответов `/api/*` на язык из `Accept-Language` (панель шлёт свой); поля с данными
  людей (имена, адреса, Common Name) не трогает. Не нашёлся шаблон — текст остаётся русским;
- **письма-оповещения** — на языке `kerio.alert_locale`, тексты событий — тем же словарём.

Новый текст в коде — новая строка словаря: в панели сборка без неё падает, на сервере текст останется
русским, пока его не добавят.

## Безопасность

- Вход — пароль (Argon2id) и TOTP для всех; опасные действия — со свежим кодом.
- Ролей нет: каждая активная учётная запись — администратор. Все эндпоинты объявляют доступ явно;
  необъявленный — `403`.
- Пароли Kerio, ключ API KMP, пароль SMTP — AES-256-GCM под мастер-ключом, привязаны к адресу (и логину):
  сменили адрес — вводите секрет заново, на чужой адрес он не уйдёт. Ротация мастер-ключа —
  `rewrap-keys`.
- TLS к KMP — полная проверка (цепочка, имя, отзыв). К Kerio — закреплённый отпечаток или УЦ с именем;
  отключить нельзя. На время установки — плюс ставящийся сертификат; всегда — плюс установленный сервисом
  как сертификат по умолчанию и сертификаты имён, **только если имя покрывает адрес администрирования**
  (иначе Kerio его там не подаёт). В режиме УЦ свои сертификаты всё равно проверяются по имени, а смена
  адреса сервера сбрасывает отметки об установке вместе с этим доверием.
- Адрес Kerio на loopback, link-local, multicast и `0.0.0.0` отвергается (проба, тест, подключение, правка) —
  нельзя заставить сервис ходить в служебные сети. Для тестов — `Kerio__AllowLoopback=true`.
- Правка и удаление сервера берут строку под `FOR UPDATE`: проход не возьмёт аренду посреди правки и не
  перезапишет её старыми значениями.
- Закрытый ключ из KMP разбирается и выгружается через свой буфер символов, который стирается сразу после
  использования; строки с ключом не создаются (кроме устаревшего PEM OpenSSL с `Proc-Type`).
- Сверка «свой ли сертификат» при признании — по сертификатам выпуска без закрытого ключа.
- Перевод ответов (`ServerTextTranslation`) — линейный: шаблоны сверяются по постоянным кускам, не регулярными
  выражениями; строки длиннее 2000 знаков не переводятся, на ответ — бюджет 200 мс; JSON буферизуется до 4 МиБ,
  выгрузки и вложения идут насквозь.
- Запрос по HTTP через доверенный прокси — `308` на HTTPS; ответы API — `Content-Security-Policy:
  default-src 'none'; frame-ancestors 'none'` и `X-Frame-Options: DENY`.
- Опубликованный мастер-ключ демо-стенда в бою не принимается — только с `KCM_DEMO_MODE=true`.
- Первый администратор подключает аутентификатор в течение часа (`SuperuserSetupWindow`).
- Настройки оповещений (`kerio.alert_*`) — ключи защиты: правка со свежим кодом.
- Проба, тест входа, «Проверить» и проверка с опросом KMP ходят в сеть по нажатию — под пределом частоты (класс `sync`):
  `RateLimits__KerioProbePerUserPerMinute` (30) и `RateLimits__KerioProbePerAddressPerMinute` (120).
- `/api/ready` решает по базе: нехватка партиций журнала пишется ошибкой в лог, но панель из-за неё не падает.
- Роль сервиса не получает прав по умолчанию: новая партиция журнала ей не правится, таблицы новых миграций получают
  права при `migrate`. База новее кода (откат образа) — предупреждение `schema_newer_than_code` в логе.
- Порты проверки — только с TLS сразу; STARTTLS и открытые (25, 587, 143, 110, 389, 80…) отвергаются:
  на них проверка не пройдёт никогда, и каждая установка кончалась бы откатом.
- Сертификат признаётся «своим» только по совпадению SHA-256 с выгрузкой из KMP, не по серийному номеру.
- Отвергнутый Kerio пароль больше не пробуется сам — нет блокировки учётной записи перебором.
- Без перенаправлений к KMP и Kerio; секреты не попадают в URL и логи.
- Контейнер: только чтение, без привилегий, роль базы без права менять схему; образ без XML-документации и
  символов отладки, `DOTNET_EnableDiagnostics=0`; базовые образы и образы стека закреплены по хешу.
- Выпуск: тесты, аудит зависимостей npm и NuGet, проверка образа Trivy (HIGH, CRITICAL), SBOM и подписанное
  происхождение сборки; Dependabot следит за версиями.

## Что учесть

- Учётная запись Kerio для сервиса — FullAdmin без второго фактора; заведите отдельную.
- Мастер-ключ храните отдельно от копий базы: без него секреты не открыть.
- KMP должен подавать сертификат доверенного УЦ (свой корень — `SSL_CERT_FILE`).
- Порты проверки — только те, что реально подают сертификат Kerio; закрытый порт в списке означал бы
  откат каждой установки (мастер подбирает их сам).
- Kerio переключает сертификат на лету; часть клиентов держит старые соединения до переподключения —
  Kerio не требует перезапуска, и сервис его не делает.
