# Kerio Connect: какие API использует сервис

Kerio Cert Manager управляет сертификатами Kerio Connect через **API администрирования** — тот же JSON-RPC, на
котором работает веб-администрирование (`https://сервер:4040/admin/`). Всё ниже проверено на
**Kerio Connect 10.0.6 (build 8504)**; где поведение расходится с документацией GFI, это сказано явно.

Весь протокол Kerio живёт в одном месте кода —
[`KerioSession`](../KerioCertManager.Modules.Kerio/Client/KerioSession.cs), доверие TLS —
[`Tls.cs`](../KerioCertManager.Modules.Kerio/Client/Tls.cs), порядок установки —
[`KerioDeployer`](../KerioCertManager.Modules.Kerio/Sync/KerioDeployer.cs).

## Соединение и вход

| | |
|---|---|
| Адрес | `https://<сервер>:4040/admin/api/jsonrpc/`, `POST` |
| Тело | JSON-RPC 2.0, `Content-Type: application/json-rpc; charset=UTF-8` |
| Вход | `Session.login {userName, password, application: {name, vendor, version}}` → `result.token` и кука `SESSION_CONNECT_WEBADMIN` |
| Дальше | каждый запрос — кука **и** заголовок `X-Token: <токен>` (защита от CSRF); токен повторяется в теле |
| Выход | `Session.logout` — в конце каждой сессии |
| Перенаправления | выключены: пароль ушёл бы на адрес из `Location` |
| TLS | закреплённый SHA-256 или цепочка УЦ с именем; отключить нельзя |
| Тайм-ауты | соединение 15 с, запрос 60 с |

## Используемые методы

| Метод | Зачем |
|---|---|
| `Session.login`, `Session.logout` | Сессия |
| `Session.whoAmI` | Роль учётной записи: нужна `FullAdmin` |
| `Server.getProductInfo` | Версия Kerio — для панели |
| `ConnectCertificate.get` | Хранилище сертификатов |
| `ConnectCertificate.toSource` | Сертификат текстом PEM — по нему считается SHA-256 |
| `ConnectCertificate.importPrivateKey {fileId}` | Импорт ключа → `{needPassword, id}` |
| `ConnectCertificate.importCertificate {id, fileId, password}` | Импорт сертификата к ключу `id` |
| `ConnectCertificate.setActive {id}` | Сделать активным |
| `ConnectCertificate.remove {certificateIds}` | Уборка старых версий (по выбору, выключена по умолчанию) |

Веб-администрирование 10.0.6 работает именно с интерфейсом `ConnectCertificate` (имя менеджера
сертификатов в коде админки — `ConnectCertificate`); более общий `Certificates.*` из документации здесь
не используется.

## Загрузка файлов

Файлы загружаются в два шага — так делает и веб-администрирование:

1. `POST /admin/api/jsonrpc/upload/`, `multipart/form-data`, поле `file`, кука и `X-Token`.
   Ответ: `{"jsonrpc":"2.0","id":1,"result":{"fileUpload":{"id":"93ea4963ca","length":1732,"name":"…"}}}`.
2. Вызов метода с `fileId` из первого шага.

## Установка сертификата по шагам

1. Выгрузить из KMP сертификат (PEM, при одном листе — ещё и P7B ради цепочки), закрытый ключ и пароль
   к нему.
2. Локально: открыть ключ (PKCS#1, PKCS#8, зашифрованный PKCS#8, устаревший PEM OpenSSL с
   `Proc-Type: 4,ENCRYPTED`), проверить, что он подходит к сертификату, что сертификат покрывает имя и
   действует, собрать цепочку лист → промежуточные (без корня). Отказ здесь — Kerio не трогается вовсе.
3. Войти в Kerio; найти сертификат, который сейчас подаётся по TLS, — по SHA-256 из `toSource`.
4. Загрузить ключ **открытым PKCS#8** (проверенный вид) → `importPrivateKey`; загрузить лист с цепочкой →
   `importCertificate`.
5. Найти импортированный в хранилище по SHA-256 → `setActive`.
6. Ждать (`kerio.verify_seconds`, 60 с), пока **все** проверяемые порты подадут новый сертификат.
7. Не дождались — `setActive` на прежний и проверка, что он снова подаётся.

На время установки сессия доверяет и закреплённому отпечатку, и ставящемуся сертификату: Kerio
переключает порт посреди сессии, и новое соединение увидит уже новый сертификат.

### Сертификаты имён (SNI)

С 9.0.2 Kerio хранит сертификаты разных имён и выбирает подходящий сам (руководство GFI «Configuring SSL
certificates»). Как именно — проверено на тестовом 10.0.6 (31.10.2026, протокол опытов ниже): для имени из
SNI подаётся сертификат этого имени, а из нескольких действующих версий — **та, что истекает позже** (не
последняя загруженная и не с большим номером); нет своего — подстановочный; нет и его — сертификат по
умолчанию. Сертификат своего имени сервис ставит так:

1. Рукопожатие **без SNI** — какой сертификат по умолчанию; найти его в хранилище по SHA-256. Не найден —
   не ставить: если импорт его сменит, вернуть было бы нечего.
2. Импорт ключа и сертификата (как выше). По умолчанию импорт не меняет — это проверяется рукопожатием
   без SNI; сменился бы — `setActive` прежнего и проверка на всех портах.
3. Удалить прежние версии этого имени (кроме нового и сертификата по умолчанию): иначе перевыпуск с более
   ранним сроком не подавался бы — Kerio держал бы ту версию, что истекает позже.
4. Рукопожатие **с именем в SNI** на всех портах: подаётся новый. Нет — отказ с советом перезапустить
   службу Kerio Connect; новый остаётся в хранилище.

Для подстановочного `*.example.com` имя для SNI — `kcm-check.example.com`.

## Особенности 10.0.6, которых нет в документации

⚠ Всё это проверено на тестовом сервере 10.0.6 (build 8504) опытами 31.10.2026; эмулятор стенда
([`KerioEmulator`](../KerioCertManager.Emulators/KerioEmulator.cs)) воспроизводит каждую особенность, и тесты
модуля гоняют установку против него по настоящему HTTPS. Прежняя запись «импорт сразу делает сертификат
активным» была выводом из метки в списке, а не из рукопожатия, и не подтвердилась.

| Поведение | Что из этого следует в коде |
|---|---|
| Метка `ServerCertificate` в `get` — **сертификат по умолчанию**: его подаёт порт без SNI; `ActiveCertificate` — любой другой действующий, включая встроенный `server` | «По умолчанию» ищется по метке `ServerCertificate`; уборка старых версий не смотрит на `ActiveCertificate`/`InactiveCertificate` |
| `importCertificate` кладёт сертификат в хранилище, **сертификат по умолчанию не меняет** — но клиентам по имени из SNI новый подаётся сразу, если истекает позже прежнего | После импорта сертификата по умолчанию нужен `setActive`; отказ после импорта — через откат |
| `setActive` делает сертификатом по умолчанию сразу на всех портах; на текущий по умолчанию — ничего не делает | Откат — `setActive` прежнего; не подтвердился — через новый и обратно |
| ⚠ **Через ~25 с после импорта или удаления** Kerio перезапускает HTTPS: 4040 и 443 несколько секунд отказывают в соединении (IMAPS 993 — нет), а **все сессии API истекают** (`-32001 Session expired`). `setActive` этого не вызывает | Сессия входит заново сама и повторяет вызов ([`KerioSession`](../KerioCertManager.Modules.Kerio/Client/KerioSession.cs)); проверка по TLS пережидает отказы соединения; `-32001` — не отказ пароля |
| Сертификат по умолчанию удалить нельзя: `remove` отвечает `{"inputIndex":0,"code":1003,"message":"Cannot delete the default certificate."}` | Отказы `remove` читаются из `message` |
| Поля `fingerprint`, `fingerprintSha1`, `fingerprintSha256` в `get` **пустые** | Отпечаток считается из `toSource` — каждый проход заново: номера `serverN` Kerio раздаёт повторно |
| Месяц в `validPeriod` — **с нуля** (январь = 0) | Учтено в разборе |
| `toSource` отдаёт только лист, без цепочки | Сравнение — по листу |
| Неверный пароль — **HTTP 200** и `error.code = 1000` «Username or password is not correct.» | Распознаётся как отказ входа; сервис перестаёт входить сам до смены пароля |

### Протокол опытов (тестовый 10.0.6, 31.10.2026)

| Действие | Что увидели |
|---|---|
| Импорт `kcm-lab.test` v1 | Без SNI — по-прежнему рабочий сертификат по умолчанию; с SNI `kcm-lab.test` — v1 на 4040, 443, 993, 995, 465. Через ~25 с 4040 и 443 перезапустились |
| `setActive` на текущий по умолчанию | Ничего |
| Импорт v2 (срок дальше) | С SNI — сразу v2, хотя v1 ещё в хранилище |
| Удаление v1 | Сертификат по умолчанию не изменился |
| Импорт v3 (срок ближе, номер `server2`), затем v4 (срок ещё ближе, номер `server3`) | С SNI — по-прежнему версия с самым дальним сроком |
| `setActive` на v2 | v2 сразу подаётся без SNI на всех портах, метка `ServerCertificate` переехала на неё |
| Удаление сертификата по умолчанию | Отказ `1003 Cannot delete the default certificate.` |
| Сессия после импорта | Работает ~25 с, затем `-32001 Session expired` на всё |
| `setActive` и сессия | Сессия живёт, перезапуска нет |
| Kerio Cert Manager: сертификат имени `webmail.demo.local` | Установлен, по умолчанию не изменён, по SNI подаётся на всех портах; продление — новая версия, прежняя убрана |
| Kerio Cert Manager: сертификат по умолчанию `mail.demo.local` | Установлен и проверен на всех портах; следующий проход после перезапуска HTTPS вошёл новой сессией, отпечаток перезакреплён |

После опытов сервер возвращён в исходное состояние: прежний сертификат по умолчанию, встроенный `kerio`.

## Ошибки

| Код | Что значит | Что делает сервис |
|---|---|---|
| `1000` на `Session.login` | Логин или пароль не приняты | `auth_rejected`, письмо, сам больше не входит |
| `-32001` | Сессии нет или истекла | Ошибка проверки |
| `1004` | Нет прав | Письмо «нет прав», установка не начинается |
| `1002` | Не найдено (сертификат, файл, ключ) | Отказ шага |
| `1000` на импорте | «key is not valid for imported certificate», «already imported» | Отказ шага; уже импортированный ищется в хранилище и активируется без повторного импорта |
| `-32601` | Метода нет — не та версия Kerio | Отказ с указанием метода |
| `-32602` | Параметры не приняты | Отказ с текстом Kerio |
| HTTP не 200, сеть, TLS | — | Ошибка проверки; письмо «недоступен» со второго сбоя подряд |

## Права учётной записи

Импорт и активация сертификата доступны только роли **FullAdmin** (полное администрирование). Роль видна
в карточке сервера; с другой ролью сервис не начинает установку и пишет об этом. Второй фактор у этой
учётной записи должен быть выключен — вход идёт по API.
